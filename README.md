# 今天晚饭吃什么

给它一句"我手头有什么"，它给你几道菜，每道菜配一条 B 站做饭视频。

纯后端服务，没有前端页面。输入是一句自然语言，比如：

> 我现在有番茄，豆腐，葱，请你推荐我今天晚上吃什么

输出是一段**可以直接读的文字**，列出若干道菜，每道菜附一条视频链接——视频是按投币、点赞、播放量三个维度选出来的，不是搜索结果里的第一条。

> **状态：可用。** B 站检索与打分链路已实测跑通。

## 它是怎么工作的

```
用户输入
   │
   ▼
① LangChain + DeepSeek  →  菜名数组
   │
   ▼
② B 站搜索（每个菜名独立并发检索）
   │
   ▼
③ 打分选优  →  每个菜只留一条最合适的视频
   │
   ▼
④ 渲染成文本（交模型润色，出错退回模板）
   │
   ▼
响应：一段可以直接读的话
```

各环节互相独立，可以分别调试和测试——这正是它被拆成四段的原因。

**为什么要有第 ③ 步。** B 站搜"番茄炒蛋"，结果里混着探店 vlog、合集、纯音乐剪辑。这些视频播放量往往还很高。所以不能只看数据，得先剔掉两类：跟菜名对不上的（相关性），和一条视频教好几道菜的（合集）——后一种点进去还得自己拖进度条找对应的菜。剩下的才按数据排。

**为什么三个指标不能直接相加。** 一条视频的播放量通常是投币数的几十上百倍，直接加权的等于只看播放量。所以要先做归一化再加权。

**另外，B 站的搜索接口不返回投币数。** 只有播放量、点赞和收藏。所以程序实际上是两段式：先按播放量和点赞粗排，再对少量候选单独查一次详情拿投币。

**菜的顺序也按这套数据排。** 视频热度高的菜排在前面，没找到视频的垫底。这里得在选中的几条视频之间重新算一遍分数——每道菜内部那个分数是在各自那批候选里归一化出来的，各家的第一名都接近满分，跨菜比没有意义。

**为什么输出里没有播放量。** 播放量、点赞、投币、视频标题、UP 主都不进最终文字，只看一眼"今晚吃什么"的人不关心这些，写在推荐里只是噪音。输出只要三样：菜名、推荐理由、链接。

**但链接仍然不经过模型的"理解"。** 链接错一个字就打不开，所以要求模型原样照抄，产出后校验每个菜名和链接还在不在，少一个就退回模板渲染。模型负责把话说顺，链接不经过它改写。

## 快速开始

```bash
.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
.venv/Scripts/python.exe main.py                              # 启动
```

用 PyCharm 的话，直接对着根目录的 `main.py` 点绿三角就行，效果一样。

想要改完代码自动重启，改用 uvicorn 命令：

```bash
.venv/Scripts/python.exe -m uvicorn main:app --reload
```

如果要让局域网里其它设备也能访问，把 `app/config.py` 里的 `app_host` 改成 `0.0.0.0`。

启动后打开 http://127.0.0.1:8000/docs 可以直接在浏览器里试接口（FastAPI 自带的交互文档）。

### 配置

在项目根目录的 `.env` 里填：

```ini
DEEPSEEK_KEY=你的密钥
DEEPSEEK_MODEL=deepseek-chat
```

DeepSeek 的接口是 OpenAI 兼容的，所以走 `langchain-openai` 就行，不用装单独的 SDK。

## API

### `POST /api/recommend`

请求体是 JSON：

```json
{
  "query": "我有土豆和鸡蛋，晚上吃什么好"
}
```

**响应是纯文本**（`text/plain; charset=utf-8`），可以直接读：

```
你手头有土豆和鸡蛋，今晚这几道都能做，我一道一道给你说。

第一道是酸辣土豆丝，土豆当家，酸辣开胃又下饭，链接是
https://www.bilibili.com/video/BV1AHk1YyEH5

第二道是土豆鸡蛋饼，两样食材做成饼，晚饭主食菜都解决，链接是
https://www.bilibili.com/video/BV1Vz4y1D7nF
```

一次给 4 到 10 道菜，具体几道由模型按食材的实际情况定。每道菜只给菜名、推荐理由和一条视频链接——播放量那些数字不进输出。

### `GET /health`

存活探针，返回 `{"status": "ok"}`。

## 目录结构

```
main.py          FastAPI 入口、路由注册、并发编排
app/
  config.py      配置与可调参数
  models.py      内部数据结构
  agent.py       食材 → 菜名（LangChain + DeepSeek）
  bilibili.py    搜索 + 打分排序
  summarize.py   渲染成文本 + 模型润色 + 兜底
tests/           纯函数单测，不碰网络
```

## 日志

默认打 INFO，一次请求约七行：请求了哪些菜、模型返回了什么、每道菜选中哪条视频（含三个维度的原始数值）、总耗时。

想看清筛选过程——搜索到几条、过滤掉几条、落选的候选分数分别是多少——把级别调成 DEBUG：

```bash
LOG_LEVEL=DEBUG .venv/Scripts/python.exe main.py
```

调 `WEIGHTS` 权重时建议开 DEBUG，落选候选那行能直接看出权重是不是合理。B 站请求的细节日志默认是压掉的，不然一次请求几十行会淹没有效信息。

## 已知问题

**B 站接口的风控。** 网页版搜索接口未登录可用，只需要先取一个 `buvid3` cookie，实测不需要 WBI 签名。但这是 B 站单方面说了算的东西，随时可能收紧——真收紧了就得改成带签名的请求，或者退一步直接返回 B 站搜索页链接。

**标题近似但仍可能是另一道菜。** 搜「番茄烧豆腐」可能返回标题为「番茄烧茄子」的视频：限定语对上了，主料没对上。现在靠相关性系数压低它的分数，但如果候选集里没有更好的，它仍会被选出来。这是这套启发式方法的固有短板，要根治得引入菜谱语义匹配。

**合集过滤也是启发式。** 判「一条视频教好几道菜」靠的是标题里的烹饪动词和主料结尾字，不是真的看懂了视频。所以两头都可能出错：漏掉几个合集，或者——更糟——把正常的单菜视频误杀成「没找到合适的视频」。现在拿实测搜到过的视频钉了一组反例测试（`test_single_dish_videos_are_not_compilations`），但换个菜系未必还准。
